# 多轮追问导诊闭环设计

## 背景

当前项目已经具备基础导诊链路、前端症状输入页面、后端会话存储与 Redis 支持，也已经完成 Docker 化启动与基础联调。现阶段最需要补齐的是导诊 MVP 的核心体验：当用户初始描述不足时，系统不能直接给出模糊结论，而应先进行动态追问，在风险优先前提下收集关键信息，再生成结构化导诊建议。

本设计聚焦“实用优先”的多轮追问闭环，不引入过早产品化能力，不在本阶段引入流式 SSE、微信小程序适配、账号体系或复杂审核后台。

## 目标

- 支持基于 `session_id` 的多轮导诊会话。
- 支持风险优先的动态追问。
- 支持聊天式前端交互。
- 在信息充分时输出结构化导诊结果。
- 保持现有 FastAPI + Vue 3 + Redis 架构连续演进。

## 非目标

- 不实现完整账号登录体系。
- 不实现历史会话列表与恢复编辑。
- 不实现 SSE 流式事件协议。
- 不实现医生审核后台。
- 不在本阶段完成完整知识库或医院实时数据接入。

## 用户体验

用户先输入一段自然语言症状描述，并可附带基础患者信息。系统创建会话后，先执行安全检查与信息抽取：

- 若命中红旗症状，立即停止追问，直接返回高优先级急诊建议。
- 若未命中高风险但信息不足，系统一次只追问一个最关键问题。
- 用户以聊天方式逐条回答，系统持续更新结构化状态。
- 当核心字段补齐后，系统结束追问并给出导诊结果。

前端体验应表现为“像对话，但底层是有状态的结构化导诊流程”，避免无边界的自由聊天。

## 核心规则

### 停止规则

采用“风险优先”：

- 出现红旗症状时，立即停止追问并返回 `completed` 结果，风险等级应为高危或紧急。
- 未命中红旗症状时，仅在核心字段补齐后停止追问。

### 核心字段

第一阶段将以下字段作为“信息充分”的最小判定集：

- 症状部位
- 持续时间
- 严重程度
- 伴随症状
- 特殊人群/基础病信息

其中“特殊人群/基础病信息”允许通过已有患者档案字段和追问结果共同补齐。

### 追问策略

- 每轮只问一个问题。
- 优先追问当前最影响风险判断或科室推荐的缺失字段。
- 避免同轮提出多个并列问题。
- 已回答信息应参与后续去重，避免重复追问。

## 架构设计

### 会话模型

系统保留 `session_id` 作为整轮导诊主键。会话状态应至少保存：

- 原始症状文本
- 患者基础信息
- 已提取结构化字段
- 已回答追问列表
- 当前待问问题
- 缺失字段列表
- 当前风险等级
- 当前流程状态
- 最终导诊结果

### 后端组件职责

#### `triage router`

- 接收请求并校验参数
- 调用导诊主流程
- 返回统一响应结构
- 不直接承担流程控制逻辑

#### `session_store`

- 负责会话状态读写
- 开发环境继续支持内存兜底
- 生产/联调默认以 Redis 为主

#### `triage_graph`

- 作为主状态机
- 决定执行路径是“安全检查”“信息补全”“继续追问”还是“输出结果”
- 统一编排各领域服务

#### `safety_guardrail`

- 负责红旗症状识别
- 返回风险等级、风险原因与紧急建议
- 一旦命中高风险，应直接让流程进入完成态

#### `symptom extraction`

- 从初始描述与追问回答中持续更新结构化字段
- 维护缺失字段清单

#### `follow_up_question_generator`

- 根据缺失字段和上下文生成下一条问题
- 一次只输出一个问题
- 保证问题可直接被普通用户理解

#### `result_composer`

- 在信息充分或风险升级时输出最终结构化结果
- 负责科室建议、就医路径、准备清单、免责声明组装

## 状态机设计

第一阶段控制为四个核心状态：

- `collecting`
  - 信息不足，需继续追问
- `risk_escalated`
  - 命中红旗症状，停止追问并准备高优先级结果
- `ready_to_complete`
  - 信息已充分，开始生成导诊结论
- `completed`
  - 结果已生成并持久化

推荐流程：

1. 创建会话
2. 进入安全检查
3. 若高风险，进入 `risk_escalated`
4. 若不高风险，进行信息抽取
5. 若仍缺关键字段，进入 `collecting`
6. 追问后重复安全检查与信息抽取
7. 条件满足后进入 `ready_to_complete`
8. 输出最终结果并进入 `completed`

## API 设计

保留现有接口形态，但明确多轮语义。

### `POST /api/triage/sessions`

职责：

- 创建会话
- 返回 `session_id`

响应最小字段：

- `session_id`
- `status`

### `POST /api/triage/analyze`

职责：

- 首轮提交时，接收初始症状与患者信息
- 后续提交时，接收 `session_id` 与本轮回答
- 每次调用都推进状态机一步

请求建议分两类输入语义：

- 首轮：
  - `session_id`
  - `patient`
  - `symptom_text`
- 后续轮：
  - `session_id`
  - `answer`

响应统一分为两种：

#### `needs_follow_up`

- `status`
- `session_id`
- `question`
- `known_facts_summary`
- `missing_fields`

#### `completed`

- `status`
- `session_id`
- `risk_level`
- `emergency_advice`
- `recommended_departments`
- `care_path`
- `preparation_checklist`
- `disclaimer`
- `structured_summary`

### `GET /api/triage/sessions/{session_id}`

职责：

- 返回会话当前快照
- 供前端刷新、回显当前对话与结果

至少应包括：

- 会话状态
- 消息时间线
- 当前待问问题
- 已有结果

## 前端交互设计

前端采用聊天式问答界面，但不是完全自由聊天，而是围绕导诊状态推进。

页面建议由以下区域组成：

- 顶部说明与安全提示
- 对话时间线
- 当前输入区
- 当前会话摘要卡片
- 完成后的导诊结果卡片

### 交互流程

1. 用户输入首轮症状描述
2. 前端创建会话并提交首轮分析
3. 若返回 `needs_follow_up`，将系统问题追加到时间线
4. 用户回答问题后继续调用 `analyze`
5. 直到返回 `completed`
6. 渲染最终结果并锁定会话输入或切换为“重新开始”

### 前端状态

前端至少维护：

- `sessionId`
- `messages`
- `currentStatus`
- `currentQuestion`
- `result`
- `submitting`

### 聊天气泡建议

- 用户消息与系统消息分开渲染
- 系统追问单独高亮
- 急诊建议使用强警示样式
- 最终结果与对话流分块展示，避免结果被聊天消息淹没

## 错误处理

### 后端

- 会话不存在时返回明确错误
- 已完成会话再次提交答案时返回可解释错误
- 无法解析回答时，不应静默失败，应返回“需要澄清”的追问

### 前端

- 网络失败时保留当前输入
- 后端错误应显示用户可理解提示
- 防止重复提交

## 测试策略

### 后端测试

至少新增以下测试：

- 首轮高风险直接完成
- 首轮信息不足返回 `needs_follow_up`
- 回答追问后补齐字段并完成
- 会话状态在 Redis 中正确更新
- 已完成会话不可继续回答

### 前端测试

当前阶段可先以手工联调为主，至少覆盖：

- 首轮输入后显示追问
- 多轮回答后显示最终结果
- 高风险场景直接显示紧急建议
- 刷新页面后通过会话接口恢复当前状态

## 实施顺序

建议按以下顺序推进：

1. 扩展后端 schema，明确 `needs_follow_up` 与 `completed`
2. 扩展 `session_store` 的会话结构
3. 重构 `triage_graph` 为四态状态机
4. 新增追问生成逻辑
5. 增补后端测试
6. 改造前端页面为聊天式时间线
7. 联调并修正文案与边界场景

## 风险与权衡

### 不使用 SSE

本阶段不引入 SSE，可以显著降低复杂度，代价是过程体验不如事件流丝滑，但对当前 MVP 完全可接受。

### 不做自由聊天

本设计强调“结构化追问”，而非开放式问诊对话。这样可以提高稳定性与可测试性，也更符合导诊而非诊断的边界。

### 不先做知识库

没有知识库并不阻碍多轮追问落地。先把流程闭环做稳，再引入 Milvus 与规则数据，整体风险更低。

## 验收标准

- 用户可在单个会话中完成多轮问答。
- 系统可在高风险场景下立即停止追问并给出紧急建议。
- 系统可在低风险但信息不足时动态追问。
- 系统在核心字段补齐后返回结构化导诊结果。
- 前端能正确展示追问过程与最终结果。
- 后端关键流程具备自动化测试覆盖。
