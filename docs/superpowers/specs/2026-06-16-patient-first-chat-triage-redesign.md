# 患者可用型聊天导诊重构设计

日期：2026-06-16
项目：Intelligent Diagnostic Assistant
状态：设计完成，待实现

## 1. 目标

把当前“不伦不类”的导诊页面重构为真正面向患者可用的聊天式导诊助手。

本次重构重点解决两个问题：

- UI 太像调试台，不像患者会真的使用的导诊产品
- 多轮追问太机械，患者一旦改口或补充，系统仍沿着旧问题死问

最终目标是：

- 首屏足够简单
- 聊天过程自然
- 支持患者自然纠错
- 结果页清楚、克制、可执行

## 2. 范围

### 2.1 本次包含

- 重做导诊页面为患者优先的聊天界面
- 首屏只保留症状、年龄、性别三个核心入口
- 将调试信息收纳到不打扰主流程的位置
- 改进多轮追问逻辑，使其支持自然改口和上下文重算
- 减少重复追问与机械字段轮询

### 2.2 本次不包含

- 不新增微信小程序端
- 不做语音输入
- 不引入复杂的消息流式输出
- 不做医生侧专门后台

## 3. 核心原则

### 3.1 主流程只服务患者

页面最重要的是：

- 患者能快速开始
- 患者能看懂系统在问什么
- 患者能自然改口
- 患者能拿到明确建议

LangGraph、多 Agent、LLM 诊断信息都要退到次要位置。

### 3.2 聊天优先，不是问卷伪装

虽然底层仍然是结构化采集，但表面交互要像一个会理解上下文的导诊助理，而不是一个按字段扫表的问卷机器人。

### 3.3 改口是主流程能力，不是异常分支

患者经常会：

- 说错
- 补充
- 否定前面的话
- 重新描述真正不舒服的点

系统必须支持这种自然纠错，并在纠错后重新判断当前最该问什么。

## 4. 方案比较

### 方案 A：在现有左右双栏界面上继续修补

优点：

- 改动最小

缺点：

- 产品骨架本身就不对
- 再修也很难变成“患者真的能用”

### 方案 B：重做为患者优先聊天界面（推荐）

优点：

- 可以彻底重排信息层级
- 最符合导诊使用场景
- 能直接消除调试信息挤占主流程的问题

缺点：

- 前端结构改动较大

### 方案 C：做成单页问卷

优点：

- 实现较稳定

缺点：

- 和“聊天式引导”目标冲突
- 改口体验会很差

最终选择：方案 B。

## 5. 页面结构设计

### 5.1 首屏开始

首屏只保留三个入口：

- 这次哪里不舒服
- 年龄
- 性别

其他信息全部延后到对话中按需获取。

### 5.2 主界面布局

整体改为“单主轴”聊天布局：

- 顶部：清楚的一句价值承诺
- 中部：会话主区域
- 底部：当前输入框

辅助信息以次级方式存在：

- 会话摘要
- 风险等级
- 恢复会话
- 报告入口

### 5.3 调试与诊断信息

调试信息不再常驻展开。

采用折叠区或次级信息块：

- 开发调试
- LLM 运行状态 / 配置诊断

默认存在，但不抢患者视线。

## 6. 对话逻辑设计

### 6.1 一次只问一个真正必要的问题

不再死按固定字段顺序追问。

新的追问策略：

- 优先补足最影响分诊判断的信息
- 如果患者刚刚自然补充了该信息，不再重复问
- 如果患者改口，重新排序追问优先级

### 6.2 纠错识别

重点识别这类表达：

- 不是 A，是 B
- 刚才说错了
- 不是这个症状
- 没有那个情况
- 主要是另外一个部位不舒服

识别到后：

- 用新信息覆盖旧信息
- 被否定的症状从当前判断中移除或降权
- 重新计算缺失字段
- 重新决定下一问

### 6.3 避免蠢重复

如果患者的上一条回答明显不是在回答当前问题，而是在改口或补充新主诉：

- 系统不应机械重复原问题
- 应转而根据新主诉继续追问

例如：

- 原问题问严重程度
- 患者回答“刚才说错了，不是发烧，是喉咙痛三天”
- 下一问应该基于“喉咙痛三天”继续，而不是继续死问严重程度

## 7. 结果输出设计

导诊完成后要给患者四类信息：

- 推荐科室
- 为什么建议这个科
- 是否需要尽快就医
- 去之前准备什么

结果区应更像“就医建议卡”，而不是系统调试输出。

## 8. 验收标准

完成后应满足：

- 页面主视觉明显更像患者产品，而不是开发台
- 首屏只保留症状、年龄、性别三个主要输入
- 调试信息不会干扰主流程
- 改口后系统不会继续沿着旧问题死问
- 自动化测试、构建、服务验证通过

## 9. 结论

本次采用“患者优先聊天界面 + 自然纠错驱动的追问重算”方案。

它的价值不在于把界面做得更花，而在于让导诊真正具备：

- 可开始
- 可理解
- 可纠错
- 可完成
