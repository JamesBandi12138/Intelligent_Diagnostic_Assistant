## 技术思考
今天的关键设计决策：

- 背景
  - 项目已从练手框架进入模拟真实业务阶段，重点不再是“能跑”，而是“能闭环、能验证、能持续迭代”。
  - 今天的核心目标有两条：
    - 把导诊流程做成真正可交互的多轮会话
    - 把导诊结果沉淀成可复用的报告能力

- 方案比较
  - 导诊流程
    - 方案 A：单接口反复调用，前端自行拼状态
    - 方案 B：后端维护会话状态机，前端按状态展示
    - 方案 C：SSE/流式事件驱动
  - 报告建模
    - 方案 A：每次从 `latest_result` 临时拼报告
    - 方案 B：把报告作为会话的嵌套字段
    - 方案 C：独立 `report` 资源
  - 验证方式
    - 方案 A：只看日志与命令退出状态
    - 方案 B：只做本地手工点击
    - 方案 C：自动化测试 + 构建 + 容器/HTTP 联合验证

- 最终选择原因
  - 选择“后端状态机 + 会话驱动导诊”，因为边界清晰、易恢复、易测试，也更适合后续接知识库和历史记录。
  - 选择“独立 report 资源”，因为报告生命周期独立于会话，后续扩展打印、导出、历史版本时更自然。
  - 选择“自动化测试 + 真实 HTTP 验证”的验收方式，是因为今天已经证明，仅看日志无法说明网页真实可访问。

## 问题记录

### 问题
服务日志显示启动成功，但页面和接口并不总是可访问。

### 排查过程
步骤1
先在本地直接运行后端和前端命令，确认代码本身可以启动。

步骤2
检查端口监听、容器状态和真实 HTTP 返回结果，而不是只看终端日志。

步骤3
切换为 Docker Compose 常驻运行后重新验证页面与接口连通性。

### 根因
“有启动日志”不等于“服务仍在稳定运行并对外可访问”，受限终端环境下后台进程可能被会话回收。

### 解决方案
统一使用 Docker Compose 作为稳定运行方式，并以健康检查、页面 200、真实接口返回作为最终验收标准。

### 后续预防措施
- 所有“服务已跑通”的结论必须附带真实访问证据。
- 默认保留健康检查和关键页面访问验证。

### 问题
风险识别和科室推荐对否定句处理错误，导致误判风险。

### 排查过程
步骤1
在多轮导诊联调中发现“没有发热、没有胸闷气短”仍触发高风险。

步骤2
补充失败测试，单独验证规则逻辑。

步骤3
检查关键字匹配实现，确认否定上下文未被剔除。

### 根因
规则实现过于依赖简单包含判断，没有先清洗否定短语。

### 解决方案
在风险检测和科室推荐前增加否定短语清洗逻辑。

### 后续预防措施
- 保留否定句专项测试。
- 继续补充低风险、高风险、急诊场景样例。

### 问题
前端缺少自动化测试，页面功能只能依赖人工验证。

### 排查过程
步骤1
先写导诊报告相关前端测试并执行，得到红灯：`npm test` 缺少脚本。

步骤2
补齐 `vitest`、`jsdom`、`@vue/test-utils` 和测试配置，再次运行。

步骤3
修复 Vitest mock 提升问题，并按发布顺序重新执行测试与构建。

### 根因
前端此前没有测试基础设施，也缺少对关键用户路径的最小自动化覆盖。

### 解决方案
新增 `frontend/src/views/Triage.spec.ts`，覆盖报告入口展示与报告展示两条主路径，并补充 `vitest.config.ts` 和 `package.json` 脚本。

### 后续预防措施
- 新增前端功能时默认补最小可运行测试。
- 避免只依赖手工点击验收。

### 问题
前端验证配置接入后，构建一度报出绝对路径产物名异常。

### 排查过程
步骤1
发现并行执行前端测试与构建时出现 `build-html` 路径异常。

步骤2
单独执行带 `--debug` 的构建，确认业务代码与生产配置本身可正常构建。

步骤3
重新按顺序执行测试与构建，确认问题来自验证方式干扰，而非实际发布产物错误。

### 根因
并行验证时工具工作目录与 Vite/Vitest 解析路径发生干扰，导致构建阶段拿到异常路径信息。

### 解决方案
将发布前验证改为顺序执行：前端测试、前端构建、后端测试、HTTP 可达性检查。

### 后续预防措施
- 对 Vite/Vitest 相关校验优先使用顺序验证。
- 将“并行跑命令”与“真实发布路径”分开处理。
