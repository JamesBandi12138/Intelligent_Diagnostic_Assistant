## 技术思考
今天的关键设计决策：

- 背景
  - 项目已从练手框架进入模拟真实业务阶段，重点不再是“能跑”，而是“能闭环、能验证、能持续迭代”。
  - 今天新增的核心目标是在不破坏现有 API 的前提下，把导诊主链路升级为可讲解、可观察、可测试的 `LangGraph + 多Agent` 版本。

- 方案比较
  - 导诊编排
    - 方案 A：继续维护手写状态机
    - 方案 B：`LangGraph StateGraph + 单 Supervisor + 多 Specialist Agent`
    - 方案 C：自治式多 Agent Network
  - Agent 决策
    - 方案 A：纯规则
    - 方案 B：规则兜底 + LLM 辅助
    - 方案 C：LLM 主导
  - 知识库接入
    - 方案 A：直接把 Milvus 强接进主链路
    - 方案 B：先让 `Knowledge Agent` 真实进图，但允许返回空结果

- 最终选择原因
  - 选择 `LangGraph StateGraph + 单 Supervisor + 多 Specialist Agent`，因为结构清晰、易讲解、易测试，也最适合从现有代码平滑升级。
  - 选择“规则兜底 + LLM 辅助”，因为导诊主流程必须稳定，LLM 更适合做追问润色、解释增强和知识摘要。
  - 选择“Knowledge Agent 先真实进图，但 Milvus 先允许空结果”，因为这样能先跑通架构和调试轨迹，再逐步增强知识检索能力。

### 问题
服务日志显示启动成功，但页面和接口并不总是可访问。

### 排查过程
步骤1
先在本地直接运行后端和前端命令，确认代码本身可以启动。

步骤2
检查端口监听、容器状态和真实 HTTP 返回结果，而不是只看终端日志。

步骤3
切换为 Docker Compose 常驻运行后重新验证页面与接口连通性。

### 根因
“有启动日志”不等于“服务仍在稳定运行并对外可访问”，受限终端环境下后台进程可能被会话回收。

### 解决方案
统一使用 Docker Compose 作为稳定运行方式，并以健康检查、页面 200、真实接口返回作为最终验收标准。

### 后续预防措施
- 所有“服务已跑通”的结论必须附带真实访问证据。
- 默认保留健康检查和关键页面访问验证。

### 问题
LangGraph 重构后，落盘节点一度导致多条后端链路在最后一步统一报错。

### 排查过程
步骤1
先跑新增的后端红灯测试，确认 `current_agent` 等新字段缺失。

步骤2
完成 LangGraph 实现后跑全量后端测试，发现大量链路在 `persist_state` 阶段失败。

步骤3
检查图节点实现，定位到会话复用和请求上下文落盘代码有遗漏。

### 根因
`persist_state` 阶段错误地依赖未定义变量，并且首轮未显式传 `session_id` 时存在重新创建会话的风险。

### 解决方案
让 `persist_state` 基于 graph state 中的 `session_id` 和 `request` 做统一落盘，并把状态、轨迹、调试信息集中写回 `session_store`。

### 后续预防措施
- 图式编排改动后必须跑全量后端测试，而不能只看新增用例。
- 所有持久化节点都要优先检查会话复用和上下文一致性。
