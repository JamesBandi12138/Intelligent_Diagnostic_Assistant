# 导诊报告生成设计

## 背景

当前系统已经支持多轮追问式导诊，能够在高风险场景下快速停止追问并给出急诊建议，也能在低风险场景下通过补全信息后生成结构化导诊结果。下一步需要把“导诊结果”提升为“可回看、可复用、便于患者和医生快速理解”的独立报告资源。

这份报告不是诊断报告，也不是治疗方案，而是一份诊前导诊摘要，用于帮助患者整理就医前信息，并帮助医生在有限时间内快速获得主诉、风险提示和关键背景。

## 目标

- 基于已完成的导诊会话生成一份独立报告。
- 报告同时面向患者和医生，包含“医生速览”和“患者说明”两部分。
- 报告通过独立 `report` 资源暴露，而不是仅作为会话字段临时返回。
- 同一会话在 MVP 阶段只生成一份稳定报告，不做版本分叉。
- 为后续打印页、PDF 导出、历史报告查看预留清晰扩展点。

## 非目标

- 不做 PDF 导出。
- 不做报告编辑。
- 不做报告版本管理。
- 不做报告列表分页。
- 不做上传附件、图片、检查单解析。
- 不做医生审核流。

## 用户场景

### 患者侧

患者完成导诊后，希望拿到一份容易理解的摘要，知道：

- 当前被建议去哪个科室
- 为什么这样建议
- 需要带什么资料
- 哪些情况需要尽快去医院

### 医生侧

患者到医院时，希望能给医生看一份结构化速览，帮助医生快速扫读：

- 主诉
- 持续时间
- 严重程度
- 伴随症状
- 既往史 / 特殊背景
- 当前系统识别的风险等级
- 推荐就诊方向

## 总体设计

采用独立 `report` 资源方案：

- 会话负责导诊过程和消息时间线
- 报告负责导诊完成后的结构化沉淀

报告只允许从 `completed` 状态的导诊会话生成。这样可以避免：

- 追问中报告内容频繁变化
- 草稿和正式版混在一起
- 前端误把半成品当成最终建议

## 数据结构

报告建议划分为四层：

1. 标识信息
2. 患者快照
3. 导诊摘要
4. 双视角内容

### 顶层字段

- `report_id`
- `session_id`
- `status`
- `created_at`
- `patient_snapshot`
- `triage_summary`
- `doctor_view`
- `patient_view`
- `disclaimer`

### `patient_snapshot`

用于保留生成报告当时的患者基础信息快照，避免后续会话字段变化影响已生成报告。

建议字段：

- `age`
- `sex`
- `pregnancy_status`
- `medical_history`
- `allergies`
- `medications`

### `triage_summary`

这是报告的统一摘要层，用于前端列表卡片、打印页头部和后续导出时快速引用。

建议字段：

- `chief_complaint`
- `risk_level`
- `recommended_departments`
- `care_path`
- `generated_from_session_status`

### `doctor_view`

定位是“让医生快速扫一眼就能知道重点”，应更结构化、更短、更偏事实。

建议字段：

- `chief_complaint`
- `key_facts`
  - 症状部位
  - 持续时间
  - 严重程度
  - 伴随症状
  - 特殊背景
- `risk_notes`
- `recommended_department_summary`
- `preparation_checklist`

### `patient_view`

定位是“患者能读懂、能照着准备”，应更口语化、更偏说明性。

建议字段：

- `what_this_means`
- `why_this_department`
- `what_to_prepare`
- `when_to_seek_urgent_care`

### `disclaimer`

必须明确：

- 这是一份导诊报告，不是诊断证明
- 不能替代医生面诊、检查和治疗决策
- 若出现急危重症状，应优先急诊就医

## API 设计

### `POST /api/reports`

职责：

- 基于已完成导诊会话生成报告

请求最小字段：

- `session_id`

行为规则：

- 若会话不存在，返回 `404`
- 若会话未完成，返回 `409`
- 若会话已完成但尚未生成报告，创建报告
- 若同一会话已生成报告，直接返回已有报告

推荐响应：

- `report_id`
- `session_id`
- `status`
- 报告主体

### `GET /api/reports/{report_id}`

职责：

- 获取单份报告详情

行为规则：

- 若报告不存在，返回 `404`
- 若存在，返回完整报告结构

### `GET /api/triage/sessions/{session_id}` 扩展

当前会话详情建议扩展增加：

- `report_id`

作用：

- 前端可以知道当前会话是否已经生成报告
- 避免重复点击生成时必须盲调报告接口

## 生成时机

报告只允许在导诊完成后生成。

原因：

- 逻辑清楚，报告内容稳定
- 避免草稿和正式版并存
- 便于后续缓存和去重
- 有利于测试和验收

本阶段不支持追问中的草稿报告。

## 存储策略

### MVP 方案

优先复用当前 Redis 会话体系附近的轻量存储模式，先把报告作为独立对象存储在 Redis 中。

建议键模式：

- `ida:report:{report_id}`
- `ida:session-report:{session_id}`

这样可以：

- 通过 `report_id` 直接读取报告
- 通过 `session_id` 查到对应报告

### 后续演进

如果后面进入历史记录、筛选、列表分页阶段，再迁移到关系型数据库更合适。

因此当前设计应保证：

- 报告数据结构独立
- 存储层有清晰接口
- 不把报告逻辑深埋在会话对象里

## 后端组件职责

建议新增 `report_generation` 相关服务，职责拆分如下：

### `report router`

- 提供 `/api/reports` 接口
- 做参数校验和错误映射
- 不负责报告拼装细节

### `report store`

- 负责报告读写
- 提供按 `report_id` 查询
- 提供按 `session_id` 查询

### `report generator`

- 基于已完成会话组装报告
- 从会话中提取患者快照、最终导诊结果、消息时间线和结构化字段
- 生成医生视角与患者视角内容

## 报告生成逻辑

报告应主要依赖以下现有数据来源：

- 会话中的患者信息
- 会话中的最终导诊结果
- 会话中的结构化提取字段
- 会话消息时间线

推荐生成顺序：

1. 校验会话已完成
2. 读取现有报告映射，若已有则直接返回
3. 从会话构建 `patient_snapshot`
4. 从最终导诊结果构建 `triage_summary`
5. 从结构化字段和消息构建 `doctor_view`
6. 从导诊结论和风险说明构建 `patient_view`
7. 写入报告存储并回写 `session_id -> report_id` 映射

## 前端展示

MVP 阶段前端不需要复杂路由体系，只需支持以下交互：

- 在导诊完成后显示“生成报告”按钮
- 点击后调用 `POST /api/reports`
- 报告生成成功后展示报告详情区
- 如果当前会话已有 `report_id`，则优先展示“查看报告”

页面建议结构：

- 报告头部
  - 报告编号
  - 风险等级
  - 推荐科室
- 医生速览区
- 患者说明区
- 免责声明区

## 错误处理

### 后端

- 会话不存在：`404`
- 会话未完成：`409`
- 报告不存在：`404`
- 存储异常：`500`

### 前端

- 报告生成失败时保留当前导诊结果视图
- 如果是“会话未完成”，给出明确提示，不允许用户误解为系统出错
- 如果已有报告，优先回显已有报告而不是反复失败

## 测试策略

### 后端测试

至少覆盖：

- 已完成会话可生成报告
- 未完成会话不能生成报告
- 同一会话重复生成时返回同一份报告
- `GET /api/reports/{report_id}` 可正确读取报告
- 报告内容包含医生视角和患者视角字段

### 前端验证

至少覆盖：

- 导诊完成后能触发生成报告
- 生成后页面能展示完整报告
- 刷新后仍能通过 `report_id` 找回报告
- 未完成状态下不会展示可用的报告生成按钮

## 风险与权衡

### 先不做 PDF

这是刻意控制范围。当前先把报告“生成对、存得住、看得到”做好，比直接冲 PDF 更稳。

### 先不做版本管理

MVP 阶段同一会话只保留一份报告，能简化接口和状态管理。后续若要支持重新生成，再增加版本号更合理。

### 报告不是诊断

文案必须持续克制，尤其在医生速览区，也只能表达“主诉整理、风险提示、导诊建议”，不能越界为明确诊断或治疗决策。

## 验收标准

- 只有已完成导诊会话才能生成报告
- 同一会话重复生成只返回同一份报告
- 报告包含医生速览和患者说明两部分
- 前端可以从导诊完成结果页进入报告查看
- 报告可通过独立 `report_id` 读取
- 后端具备自动化测试覆盖核心生成与读取流程
